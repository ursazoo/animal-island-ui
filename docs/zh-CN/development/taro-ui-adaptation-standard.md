# Taro 移动端 UI 改造标准

版本：1.0 · 日期：2026-10-14 · 适用仓库：`ursazoo/animal-island-ui`

源码基线：`79810934ee9d08c22044d34e06f8bba40391207b`。本文定义后续改造要求，不表示 Taro 组件、预览站或真机验证已经完成。

## 1. 目标与范围

直接改造 fork 的 UI 库，使 Taro + React 微信小程序可以安装并使用它，同时保持原有海岛风格、采用移动端交互。配套提供可以实际操作的浏览器预览站和微信小程序预览工程。

- 成果落在库的组件源码、样式、导出、类型、构建、文档和 Skill 中。
- 预览工程使用库组件，不另写一套用于展示的组件实现。
- 当前范围为 39 个原有组件模块中的 38 个迁移；`Cursor` 在小程序不适用。完整清单见第 5 节。
- 原 Web 入口默认保留，用于现有使用方式、回归和视觉对照。这是当前技术选择，不是用户明确提出的双端支持要求。
- `ActionSheet`、`TabBar`、下拉刷新、多选 Select 等新增公共能力不计入本次原组件迁移；新增时另行说明范围。内部 Picker、弹层宿主等可作为实现基础，不冒充原有公共组件。

## 2. 规则来源与冲突处理

用户当前明确要求优先。其余按照仓库 `AGENTS.md`：组件源码、样式和配置优先于文档。源码用于确认现有行为，不阻止本文明确要求的移动端交互变更。

| 来源                                                                                       | 负责定义什么                                  |
| ------------------------------------------------------------------------------------------ | --------------------------------------------- |
| `src/components/<Name>/` 与实际运行效果                                                    | 现有组件的外观、变体、状态和行为基准          |
| `src/styles/variables.less`、`src/styles/themes/default.less`                              | 编译期设计变量及运行时主题映射                |
| [原设计规则](../design-system/design-rules.md)、[逐组件规范](../design-system/components/) | 视觉意图和精确实现参考；发现差异后核对源码    |
| `skills/animal-island-ui-style/SKILL.md` 与组件引用                                        | 现有 Web 使用方式、视觉约束及 API 提示        |
| 本标准                                                                                     | Taro 迁移、移动交互、预览、产物消费与验收要求 |

**沿用原库的要求**：视觉语言、设计变量、组件变体、字体图标来源、真实 API 优先。

**本次新增的要求**：Taro 导出与构建、触屏交互、对照预览、真实打包消费、微信端验证及差异记录。

已发现的基线差异必须按以下方式处理：

- 主色体系包含薄荷绿，但当前 `Button` 主按钮样式使用奶油色。不能将所有主按钮改为薄荷绿来“符合风格”。
- `50px` 是胶囊圆角说明，不是控件高度。按钮不同尺寸存在实际圆角覆盖；以对应尺寸的源码为基准。
- `Modal` 有 `default` 圆角和 `game` 异形变体；当前函数默认值是 `game`，其属性注释却写 `default`。按运行值建立基准，适配该组件时同步修正文档和注释。
- `Drawer` 的部分动效说明与通用动效规则不一致；核对该组件源码和实际动画，不能用一条通用时长替换全部效果。
- Input 的显式阴影、错误/警告状态，以及 Switch 的内阴影都有各自规则；不能概括成“非主按钮全部禁用阴影”。

每项冲突记录文件、基线值、移动端处理和理由；在处理对应组件时同步相关中英文文档，避免本次顺带重写所有上游文档。

## 3. 美术一致性

### 3.1 改造前建立基准

每个组件开始迁移前，读取源码、样式、类型和对应设计规范；运行原组件，保存适用变体与状态的参考截图。动画另保留短录屏或可复现操作。

基准记录必须包含源 commit、组件与 props、视口、字体加载结果、截图或录屏位置。已有源码结论不能冒充已完成的运行截图。

### 3.2 保持的视觉特征

- 继承原组件的暖色背景、棕色文字和配色关系；状态色、装饰色及现有深色场景按该组件基准保留。
- 保持按钮和输入框的圆润形态、标题丝带、弹窗对应变体的轮廓，以及卡片图案等识别特征。
- 保持各组件自己的描边、阴影分配、字号层级、字重和图标比例。卡片默认无阴影；主按钮立体阴影、其他按钮柔和阴影等依实际变体处理。
- 字体以原 Nunito + Noto Sans SC 为目标；图标和插画保留原素材的造型、配色和授权信息。
- 保持实际组件的动效节奏和按压反馈。触屏取消依赖悬停的操作，H5 仍保留适用的键盘焦点与可访问性。

精确色值和尺寸从原定义读取，不在本文维护第二套数值表。新增移动容器、Picker 高亮区、按钮栏使用同一套设计变量和已有组件。

### 3.3 平台适配的边界

- 可调整布局方向、弹层位置、内容滚动、密度和实际触摸区域，以支持手指操作；这些变化需与视觉改动分开记录。
- 本项目将小控件的有效点击区域目标设为至少 44 × 44 个逻辑像素，允许扩大外层点击区域，不机械放大可见图标。
- 在写样式前确定尺寸基准与转换策略；核对消费者的 `designWidth`、样式转换和行内尺寸，避免重复换算。以渲染尺寸检查结果为准。
- 字体与图标可更换加载或渲染方式，但保留视觉目标。系统字体可以作为加载失败兜底，不能作为“视觉还原已完成”的依据。
- SVG、异形裁切或动效无法直接复用时，先验证等价实现。不可实现的差异必须在预览和记录中展示，状态标为“视觉待确认”。
- 不自动换成另一套组件库主题、emoji、通用圆角弹窗或新的装饰风格。需要显著改变已确认外观时，把可对照结果交给用户判断；常规等价适配继续自主完成。

## 4. 移动端交互契约

### 4.1 Select 与 Picker

普通短文本单选使用“原风格触发字段 → 底部抽屉 → PickerView → 确认”。保持现有 `{ key, label }`、受控 `value` 和 `onChange(key)` 的数据语义；新增参数必须以实际类型声明为准。

通过触摸滚动选择，不显示上一项/下一项按钮或重复的确认提示。Picker 使用原库暖白底色及同色遮罩，以淡薄荷绿选中条区分当前项；外层抽屉保留奶油色。

1. 每次打开从最新外部值初始化草稿；有合法值时定位到该项。空值或值失效时显示占位，抽屉有选项则高亮首个有效项，但打开本身不回填。
2. 滚动只更新草稿。确认时提交当前显示的有效 `key`，一次操作调用一次 `onChange`；不滚动直接确认也必须正确。
3. 惯性滚动尚未稳定时，确认应等待稳定值或暂不可用；不能提交旧值。具体事件能力在选定 Taro 版本核实。H5 也必须处理鼠标滚轮/触控板的滚动结束，显示项与选中条居中并同步 key 后才可确认。
4. 取消、允许关闭的遮罩点击和关闭手势均丢弃草稿，不触发值变更；再次打开从最新外部值恢复。页面卸载不得补发确认。
5. 选项更新按 `key` 保留仍有效的草稿；失效时重新定位到合法项并修正索引。外部 `value` 更新优先，并重置当前草稿。空列表显示空态且不可确认。
6. 触发字段上的清空入口在有值且可操作时直接可见；沿用 `onChange('')` 后调用 `onClear` 的顺序，阻止误触发打开。禁用状态不打开、不清空、不提交。
7. 搜索模式使用抽屉内的搜索列表；默认点击搜索框才唤起键盘。保留过滤与 `onSearch` 语义，包括关闭时清除非空查询的通知。若列表选择采用立即提交，必须明确展示和记录该模式差异。
8. 超长文案、长列表采用可读、可滚动的展示方式，不靠缩小文字解决。多选属于新增能力，不能混入单选适配。

### 4.2 抽屉、弹窗与输入

- 底部双按钮等宽铺满可用行宽，单按钮占满整行。双按钮不仅布局框对齐，可见轮廓也应对齐：该行统一使用轻阴影，hover/按压不产生垂直偏移；单按钮保留原厚底。关闭图形应清晰可见，触摸区域至少 44px。
- 底部抽屉高度限制为屏幕的 40%–75%，键盘打开时受剩余可视空间约束。滚动边界内须为外侧焦点线留出空间，尤其是首个控件。固定操作区使用不透明底色、顶部间距和向上柔和阴影，与滚动内容分隔。
- 弹层处理遮罩、层级、内容滚动、背景滚动锁定、底部安全区和关闭恢复；嵌套弹层只允许最上层响应关闭，避免提前释放背景滚动。
- 长内容保持操作按钮可达；输入框和搜索框唤起键盘后，当前字段及必要操作仍可见。关闭后恢复合理焦点和页面位置，不意外再次唤起键盘。
- 下滑关闭不是首版强制能力。若提供，只在明确区域触发，并处理与内容滚动、Picker 手势的冲突。
- 普通确认保留 Modal 的对应视觉变体；复杂内容可由调用方选择 Drawer 或完整页面，不静默把所有 Modal 改成抽屉。
- Tooltip 使用可发现的点击入口；关键内容不只放在提示里。按钮、开关、单选、多选、评分提供按压和禁用反馈。
- 保留可访问的名称、标签、状态和正确控件语义。不要为了消除默认样式，把所有 Taro Button 都换成无语义的 View。

### 4.3 数据与平台行为

- 日期、时间保留值格式、清空语义、粒度、步长和有效性约束；`disabledDate` 不得静默降级为只有最小/最大范围。日期范围用适合触屏的日历。
- Form 保留字段状态、校验与提交含义，明确适配输入事件。表格保留数据对照、列配置和操作能力，不自动改成业务卡片列表。
- Upload、Image、CodeBlock、BackTop 等通过对应小程序能力实现；保留现有回调和错误处理含义，类型差异需明确说明。
- 各组件处理空数据、加载、失败、重复操作、卸载和后台切换；定时器及临时资源正确清理。

## 6. 库结构与产物契约

- 在同一库内增加显式 Taro 入口；`animal-island-ui/taro` 和对应样式入口是目标方案，尚未实现，最终路径以产物消费验证为准。
- 原组件目录中可并列放置 Taro 渲染实现；平台无关逻辑在确有复用时提取，避免为了共享而扩大 Web 重构。
- Taro 入口和声明依赖图不应间接引入 Web 总入口、ReactDOM 弹层或仅支持 Web 的图标实现。类型适配到 Taro，不能用 `any` 或伪造 DOM 事件掩盖差异。
- 样式共享设计来源，但分别处理小程序主题作用域、选择器、字体、资源和尺寸；保留现有 Web 构建契约。
- 同步 `package.json` 的 exports、类型解析、files、peer 依赖、样式副作用标记和构建脚本。依赖与 JSX 输出策略先在选定 Taro 版本验证，不直接照搬顾问建议。
- 通过 `npm pack` 生成真实包，在独立消费者中安装，验证导出、类型、样式、资源和组件识别；源码 alias 或工作区直连不能作为交付验收的唯一证据。
- 首轮记录并固定所验证的 Taro、React、构建器、微信基础库和渲染模式版本；不据此宣称支持所有 Taro 版本、H5 浏览器或小程序渲染模式。

## 7. 预览要求

预览工程位于同一 fork，通过 Taro H5 提供浏览器预览，通过 weapp 构建提供微信预览。开发时可使用本地联调，验收时必须使用第 6 节的真实安装产物。

- 组件目录覆盖第 5 节全部模块，未完成项显示真实状态；点击已完成项必须能展示并操作。
- 展示适用的普通、按压、选中、禁用、加载、错误、空数据和长内容状态；不适用状态注明原因。
- 提供原版参考与改造版对照。比较单个控件外观时保持内容、props、比例一致；比较整体流程时明确移动布局的合理差异。
- 提供手机视口切换，至少检查 320、375、414 CSS px 三个宽度；数值只定义本项目 H5 检查范围，不代表真机覆盖。
- 提供由真实库组件组成的完整表单，验证打开、选择、确认、取消、清空、校验与提交。示例数据明确标为演示数据。
- 普通单选必须能操作抽屉内 Picker；若 H5 与微信底层实现需要分支，应放在库内，并共享值与事件契约，不能只在预览页实现替身。
- 显示当前库版本/commit，以及 H5、微信开发者工具、iOS、Android 的独立验证状态。技术信息集中在预览说明中，不混入演示表单的正常操作文案。
- 每批提供可打开的预览地址或启动方式，以及微信工程入口。仅截图、说明文档或打包成功不等于已经交付预览。

## 8. 实施顺序与验收

### 8.1 实施顺序

1. 建立原版视觉基准、平台差异记录及 Taro 产物消费链路。
2. 首批实现 Button、Card、Input、Drawer 的移动底部能力、Select，并同步可操作预览。

### 8.2 分层验证

| 检查                     | 能证明什么                                 | 不能替代什么         |
| ------------------------ | ------------------------------------------ | -------------------- |
| 源码、类型与文档检查     | API、依赖边界、引用及文档一致性            | 实际渲染和手势       |
| 与改动相关的状态测试     | 确认/取消、清空、动态选项、校验等状态行为  | 滚轮惯性与平台表现   |
| 库构建、打包、消费者构建 | 实际包可解析、可编译，样式和资源进入产物   | 运行无误或视觉一致   |
| H5 操作与截图对照        | 浏览器中的布局、状态和操作                 | 微信运行效果         |
| 微信开发者工具           | 小程序基础运行、布局与状态流程             | 真机键盘、惯性和性能 |
| iOS 与 Android 真机      | 已执行场景的字体、滚动、键盘、安全区和动画 | 未测设备和未执行场景 |

遵守仓库现有必需检查。对新增状态契约编写有意义的测试；文档或低影响外观修改不为了数量增加测试。未执行的检查写“未验证”，不能用其他层的通过覆盖。

### 8.3 单组件完成条件

- [ ] 实现、导出、类型、样式和必要资源属于库本身，并能从实际安装包使用。
- [ ] 现有适用 API 已迁移；所有差异有明确记录，没有静默丢失行为。
- [ ] 适用变体与状态有原版基准和移动端对照，字体、形状、颜色、阴影不存在未说明的变化。
- [ ] 移动端操作契约通过，空态、禁用、重复操作和资源清理有对应验证。
- [ ] 预览可打开、可操作，组合页面使用同一个库实现。
- [ ] 相关自动检查通过；H5、开发者工具、iOS、Android 结果分别记录。未完成真机验证的组件只能标为“已实现，真机待验证”。
- [ ] 文档、Skill 及中文镜像与实际 API 一致；有重大视觉差异的组件保持“视觉待确认”。

验证记录使用统一字段：`组件/变体与 props`、`源码与包版本`、`平台/设备/视口`、`操作步骤`、`预期与实际`、`截图或录屏`、`已知差异`、`结论与日期`。

整体完成意味着 38 个适用模块及其附属导出满足上述条件，`Cursor` 明确标为不适用，预览和文档同步。提交、推送、发包或部署分别报告，不由文档完成或本地构建通过推定。
